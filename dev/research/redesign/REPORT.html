Typing the inside of the pipeline: a redesign of tacit

Tacit's runtime contracts work well. Its static promises mostly don't hold. This report measures both, describes the ideal API and the language limits that block it, and proposes a design that keeps tacit thin over ibis and pandera while getting every column reference checked by pyright, mypy and ty.

pyright 1.1.414mypy 2.4.0ty 0.0.89pyrefly 1.4.0ibis 12.0.0pandera 0.34.1Python 3.13

Summary

Re-measured on today's tools, tacit's runtime half holds up and its static half largely does not:

  • Only pyright enforces tacit's types.
    • mypy: neither tacit nor ibis ships py.typed, so everything is Any.
    • ty and pyrefly: ibis defines a mixin conditionally, so every ibis Table has an unknown base class. A forgotten cast() passes silently.
  • No checker catches a typo in a column name. df.sepal_lenght is accepted everywhere, because DataFrame[S] inherits ibis's catch-all __getattr__.
  • The flagship examples fail pyright. The README's own quick example has 4 errors.

The first version of this report proposed a wrapper type and a native validator. The owner pushed back on both. The four follow-up experiments (E10–E13) changed the recommendation towards a thinner design.

Recommendation (revised)

  • Keep tacit 0.2's shape: a Schema class plus DataFrame[S], which stays a real ibis Table at runtime. Type checkers instead see a stub generated mechanically from ibis's own Table API, with the catch-all attribute lookup removed. Tacit re-implements none of ibis's API: the stub is 160 lines, needs no hand fixes, and is regenerated on every upgrade.
  • Typed columns live in a small namespace: df.c.amount.
    • Columns are declared Column[float] or Column[float | None], so names, value types and nullability are all checked.
    • The column types are generated from ibis by calling every method on sample data. A conformance harness then executes every declared method and fails CI on any type that lies.
    • The .c namespace keeps the reserved names to about 5. Putting columns on the frame itself would reserve 84 ibis method names, and each new ibis release would add more.
  • Construction carries the contract.
    • Out.build(...), Out.extend(...), a typed join and an aggregate are checked projections.
    • Forgetting to cast after any ibis operation is a type error on all four checkers.
    • @contract becomes optional, kept for data validation and error context.
  • Keep pandera as the check library, and execute its checks in one fused query.
    • This matches pandera.validate on 682 of 685 parity cases.
    • It runs one query instead of 16–30, at the speed of a native validator.
    • Propose single-query execution upstream as well. If that lands, tacit's executor can be deleted.
  • Keep ibis, with no dependency on upstream patches. Development has slowed sharply since its funded team was laid off, but it is still maintained. Pin it and test against ibis's main branch.
  • Accept the language limits. Output schemas cannot be inferred, so steps name their outputs. Pick, drop and rename need codegen.

Review questions

The owner asked five questions about the first version of this report. Four experiments (E10–E13) went back to the evidence. This section gives the answers. Where a question exposed an overstated claim, the answer says so.

1. Doesn't dropping pandera mean re-implementing every check?

Partly yes. The first report understated the work. The proposed 150–200-line native validator covered about 20% of what pandera's ibis backend does:

  • 14 of 15 built-in checks;
  • about 3 of the 28 schema-level features that work on ibis;
  • no custom checks;
  • no Check options such as ignore_na or raise_warning;
  • parity tested on only one schema.

Full parity would take about three times as much code, plus a test battery. The checks themselves are a thin slice (15 built-ins of about 5 lines each). The volume is in the options, the null and NaN semantics, and the error reporting.

The performance claim does hold:

  • Tuned pandera still runs 16–30 queries, because its ibis backend issues one query per check.
  • Tuning (lazy mode, capped failure cases, materialising the input) recovers only 1.1–1.4× of a 3–7× gap.
  • One tuning is worth doing regardless: materialising file-backed sources makes CSV validation 7.6× faster.

A hybrid keeps the "thin glue" property:

  • pandera remains the check library and spec. Users keep writing Check.ge(0), registered and custom checks keep working, and pandera's bug fixes keep flowing in.
  • tacit takes the boolean expression each pandera check builds and fuses all of them into one aggregate query.
  • It is 213 lines. It matches pandera.validate on 682 of 685 cases (re-run by the main session), and runs within 5–15% of the native validator's speed.
  • The cost is reliance on two private attributes (_check_fn, _check_kwargs). A parity battery run against every pandera release guards against breakage.

Upstream: pandera's merged spec (#2401) moves every backend onto narwhals, starting with ibis. A single-query mode fits that design, and the 41-line proof of concept shows it works. If it lands upstream, tacit deletes its executor and goes back to plain pandera at the faster speed.

2. Doesn't wrapping the ibis table re-implement a big API and add another limiting layer?

The wrapper design did add a layer, and it doesn't need to. In the first prototype (E8), users reached most of ibis through .ibis, and only about 10 methods were typed on the frame.

E13 tested the alternative. The frame is an ibis Table subclass at runtime. Type checkers see a stub that a 341-line generator copies from ibis's own Table and GroupedTable signatures, with the catch-all __getattr__ removed. The result:

  • All 102 Table members are available directly on the frame, with ibis's own annotations.
  • No hand fixes were needed. Three opt-in patches cover upstream annotation bugs.
  • At runtime nothing is wrapped: isinstance(df, ir.Table) is true, and ibis.union, create_table, joins, windows and pickling all work.

Static safety improved over the wrapper:

  • Typos in column names, in ibis method names, and inside ibis calls are errors on all four checkers.
  • Returning the result of any ibis operation where a typed frame is expected is an error on all four. The wrapper caught that only in pyright.

The stub is the reason it works. A control run without it lost the frame-level checks on mypy, ty and pyrefly.

Two costs remain:

  • The namespace. If columns sit directly on the frame (orders.amount), they share a namespace with 80 ibis members. About 25 of those are plausible column names (count, limit, cast, schema, view). Worse, a new ibis method could break existing schemas at import. Hence df.c.amount, which reserves about 5 names and can never collide with ibis.
  • Passing a frame to an ibis function annotated ir.Table (ibis.union(a, b)) works at runtime, but is a false positive on pyright and ty. The workaround is tacit.as_table(df).

3. Why is ibis less maintained, why no py.typed, and do we depend on upstream?

Why it slowed. There are two official statements from the lead maintainer, Phillip Cloud:

  • 2025-05: "the project lost most of its full time staff in September of 2024 due to layoffs." Voltron Data was the corporate sponsor, and 4 of the 5 steering-committee members worked there.
  • 2025-10: "I am not stopping maintenance myself, but I won't be working on Ibis full time."

Nobody has declared the project deprecated. A part-time group now merges PRs: Deepyaman Datta (given commit rights in March 2026), Nick Crews and Gil Forsyth. Re-counted with bots excluded:

  • Human commits are down 78% year on year.
  • There has been no release for 258 days, the longest gap in the project's history.
  • External PR acceptance fell from 68% to 20%.
  • Even so, there were 18 commits this month, and a 13.0 release plan is open.

Two precedents show what users do when upstream is slow:

  • Google's bigframes now vendors its own copy of ibis.
  • Fortnox published a package that patches typing into installed ibis.

The risk is slow velocity, not abandonment.

Why there is no py.typed. It was never refused on request.

  • The maintainers added it in 2023, then removed it themselves (#7563). mypy reported 2,746 errors, mypy was not in their CI, and they called the marker "a bit of a false promise".
  • They said they would take incremental typing PRs.
  • A 2025 request to revisit it got no maintainer reply.

Dependence on upstream: none required. Every prototype ran on unmodified ibis 12. The two one-line ibis fixes close only one gap: a raw ibis table passed where a typed frame is expected. Without them, mypy, ty and pyrefly miss that case, and the runtime still catches it. If ibis never merges them, tacit can ship a generated stub overlay; E12 tested this, and it closes the gap on all four checkers. It's better to wait for user demand first.

Mitigations:

  • Pin ibis-framework<13.
  • Run CI against ibis's main branch.
  • Keep a short exit-plan decision record. The options, in order of cost: pin or vendor (about 1–2 weeks); a native DuckDB/sqlglot backend (3–6 weeks); narwhals (4–8 weeks).

4. Is the proposed API feasible, and does it make sense for us?

This is what tacit would own and maintain under the revised design, compared with 757 lines today:

That's about three times today's code. The pattern is the FastAPI one: tacit holds the glue, generates its typing from the libraries underneath, and proves it with harnesses rather than by hand.

What does not exist yet: T2 join views (designed and built in E8, not yet ported to T2), the E9 nullability items, and a migration codemod.

The user-facing change from 0.2 is small. DataFrame[S], Schema and inheritance stay. These change:

  • x: float becomes x: Column[float].
  • Annotated[T, Nullable()] becomes Column[T | None].
  • df.x becomes df.c.x.
  • Outputs are built with Out.build(...) or Out.extend(...).

5. Is the generated column facade sound?

The first one wasn't. Despite the word "generated", the E8 facade came from a hand-written spec table. Nothing checked it against ibis. E11 built a conformance harness:

  • 5,408 cases.
  • It executes every declared method on real columns of every value family, nullable and not, on duckdb.
  • The data includes an all-NULL group, a single-row group and an empty input.
  • It compares the outcome with what each checker reports.

Against the hand-written facade it found:

  • 630 nullability lies. These are silent: comparisons, cast and reductions on nullable columns were typed as non-null.
  • 62 value-family lies. These fail at construction: for example Decimal / x is really float.
  • 17 methods whose parameters drifted from ibis. where= was missing on every reduction.
  • Coverage of about 30%. Calling an uncovered method was a hard error on all four checkers.

A derived generator fixes this. It reads method names, parameters and family membership from ibis, and finds result types by calling ibis on sample columns. Only about 70 lines of rules stay hand-written, mostly about nullability, which ibis doesn't track. On the same harness:

  • 0 nullability lies and 0 family lies.
  • False positives drop from 270 to 24.
  • Coverage rises to about 95% per family.
  • Methods it can't type precisely fall back to ibis's own annotations. The facade only adds precision; it never removes access.

Upgrade cost. Over ibis 10 → 11 → 12 → main, the public API barely changed. What changed was behaviour: for example, 64 Decimal operations started working in 12. The hand-written spec silently mis-typed those. The harness flags this kind of change automatically. Expected human work is about 0–2 rule entries per ibis release.

Residual holes, all documented:

  • bool is a subclass of int in Python, so integer arithmetic on a boolean column type-checks. Fixing it needs a marker type.
  • == across value families falls back to Python's object equality.
  • String-literal casts are loose.
  • Window functions need their own type.

Where tacit stands

What to keep

  • Schemas are Python classes. Go-to-definition, find-references, diffs and inheritance all work, and agents can find schemas without extra context files.
  • The parse / cast split. Untrusted data is coerced and validated. Trusted data gets a check that costs nothing.
  • Strict and non-nullable by default. These are the right defaults for production pipelines.
  • Structural errors at runtime are excellent. In the trial, every bug detectable at runtime was caught, with a message naming the schema.
  • Thin glue over ibis and pandera. The revised design keeps this property.

The view from a team

Picture a company with forty engineers and a few hundred pipelines, more and more of them written or edited by coding agents. Here is what they need from a contract library.

  1. Safe refactors. Renaming or retyping a column in a shared schema should flag every downstream use. Today that only works for whole-schema mismatches, and only in pyright.
  2. Feedback in seconds. Agents iterate on what the type checker and tests tell them. A mistake that surfaces only after a warehouse job is the most expensive kind. The most agent-friendly property a library can have is that wrong code fails the type check.
  3. The same answer in every checker. Teams standardise on mypy, editors run Pylance, and new projects pick ty.
  4. Cheap validation with useful reports. One scan, not one per check. Failures should name the step, the column, how many rows, and give examples. Teams should be able to quarantine bad rows instead of failing.
  5. Contracts other teams and tools can read. Schemas should be exportable, diffable for breaking changes, and inferable from existing tables.
  6. One obvious way. Today there are two styles of @contract. One of them is a type error, and it's the one in the README.

Proposed design

This section describes the E13 "T2" design: tacit 0.2's spelling with the clean stub and typed columns. It reuses E8's column facade, fields and validation, with the facade generator replaced by E11's derived one. Package: e13-thin-frame/src/tacit_t2.

Schemas and typed columns

import tacit
from tacit import Column, DataFrame, field

class Orders(tacit.Schema):
    """Orders as delivered by the order service."""
    order_id: Column[int] = field(unique=True)
    order_ts: Column[datetime]
    status: Column[str] = field(isin=["pending", "shipped", "cancelled"])
    amount: Column[float] = field(ge=0, description="gross, EUR")
    discount: Column[float | None]                     # nullable is spelled | None
    count: Column[int]                                 # fine: columns never collide with ibis

orders: DataFrame[Orders] = Orders.parse(con.read_csv("orders.csv"))
orders.c.amount                # Column[float]
orders.c.status.mean()         # error on all 4: no mean() for Column[str]
orders.c.discount.fill_null(0) # Column[float | None] → Column[float]
orders.c.discount > 0          # Column[bool | None]: nullability propagates
orders.group_by("status").agg(n=orders.c.order_id.count())   # full ibis API, returns ir.Table
  • The frame is an ibis Table. Every ibis method works at runtime and is typed by ibis's own annotations, through the generated stub. Schema-preserving operations (filter, order_by, limit, distinct, cache) return the same DataFrame[S]. Everything else returns a plain Table, and you re-enter with build, extend, conform or parse.
  • Why .c. Column names never compete with ibis's 80 members, so count, schema and view are valid columns, and new ibis releases can't break schemas. The cost is two characters per access.
  • Why Column[T] with Python value types. One generic type gives readable hovers, keeps int and float apart, and carries nullability. Statically it is the derived facade; at runtime it is the plain ibis expression.
  • Subtyping. DataFrame[S] is covariant, so a DataFrame[Order] is accepted where a DataFrame[RawOrder] is expected. Input boundaries check "at least these columns" and project to the declared ones, so the body sees an exact schema. Outputs are strict.

Boundaries

orders = Orders.parse(con.read_csv("orders.csv"))   # coerce + all checks in one query; file sources materialised once
orders = Orders.conform(con.table("orders"))       # structural only, no query; NOT NULL- and timestamp(6)-aware

Construction is the contract

class NetAmount(tacit.Schema): net_amount: Column[float]
class NetOrders(Orders, NetAmount): pass

def add_net(o: DataFrame[Orders]) -> DataFrame[NetOrders]:
    return NetOrders.extend(o, NetAmount.build(net_amount=o.c.amount - o.c.discount.fill_null(0)))
    # missing / extra / wrongly typed / nullable delta column: error on all 4
    # `return o.mutate(...)`: error on all 4 (Table is not DataFrame[NetOrders])

Aggregation and joins come from E8, and neither is ported to T2 yet. Aggregation uses an explicit Out.aggregate(by=[...])(...), so a forgotten .sum() raises instead of silently becoming a grouping key. Joins use a typed join scope: j.left and j.right are typed views, and the output constructor names every column.

Reusable steps

def latest_per_key[S: tacit.Schema](df: DataFrame[S], key: Column[Any], ts: Column[datetime]) -> DataFrame[S]:
    return df.filter(tacit.row_number().over(group_by=key, order_by=ts.desc()) == 0)

class HasEventTs(tacit.Schema): event_ts: Column[datetime]
def recent[S: HasEventTs](df: DataFrame[S], since: datetime) -> DataFrame[S]:
    return df.filter(df.c.event_ts >= since)

Validation and errors

Orders.parse: 2 issues for Orders
  - amount: constraint ge(0) failed; 3 rows; e.g. ['-33.74', '-1.0', '-5.5']
  - status: constraint isin(['pending', 'shipped', 'cancelled']) failed; 1 row; e.g. ['refunded']

In the proposed implementation, field(ge=0, isin=...) builds pandera Check objects lazily, and field(checks=[pa.Check...]) accepts any pandera check, registered custom checks included. tacit executes them all in one query, as E10's hybrid does today. There is a single ValidationError with structured .issues. The optional @tacit.step adds step names, data validation at boundaries, and runtime checks for untyped callers.

Usability trial (E9)

A fresh agent wrote a ride-hailing pipeline from the prototype guide alone, without reading the library source. It planted six bugs:

  • All five that a type checker can catch were caught by every checker.
  • There were zero false positives on the correct code.
  • It rated its confidence at 7/10, and 9/10 for names, types and frames.

The points it lost were nullability narrowing after a filter, reductions over nullable columns, missing duration arithmetic, and column handles not tied to their frame in generic steps. E11's derived facade fixes the reduction soundness, and gives duration arithmetic ibis's own interval types. Narrowing (assume_not_null(), checked at output) is on the roadmap.

Known limits

  • Raw ibis tables. A raw ir.Table passed where a frame is expected is missed by mypy, ty and pyrefly until two one-line ibis fixes land (or a stub overlay ships). The runtime catches it.
  • Passing a frame to ibis functions annotated ir.Table gives false positives in pyright and ty. Use tacit.as_table(df).
  • Untyped intermediates. After an ibis operation, a plain Table falls back to ibis's own typing quality until you re-enter tacit.
  • Facade holes: bool is a subclass of int, cross-family ==, loose string-literal casts, and window-function types.
  • Joins. T2 join views are not yet built, and outer-join nullability is not yet in the types.

Roadmap

  1. Phase 0: fix what ships (0.2.x, no API break)

    • Ship py.typed.
    • cast(): become NOT NULL- and timestamp-precision-aware; memoise the target schema (128 → 4 µs).
    • Make X | None mean nullable.
    • @contract: resolve hints lazily; raise on annotations it can't enforce; support generics.
    • Errors: include counts, sample values and step names.
    • Docs: be honest about which checker supports what.
    • CI: run the typechecking suite on all four checkers.
    • Pin dependencies: ibis-framework<13, polars<2, pandera>=0.31.
    • Add a CI job against ibis main.
    • Do a trial docs build on Zensical before Material reaches end of life on 2026-11-05.

  2. Phase 1: validation (0.3)

    • Hybrid executor: pandera checks in one fused query, with the 685-case parity battery in CI against every pandera release.
    • Materialise file-backed sources.
    • Lazy pandera import.
    • Structured ValidationError.issues.
    • filter_valid.
    • Open the batching issue on pandera.

  3. Phase 2: typed frames (0.4, then 1.0)

    • Generated Table stub (DataFrame[S] keeps its runtime ibis base).
    • Derived Column[T] facade, with the conformance harness gating CI.
    • df.c.
    • build, extend, aggregate(by=) and the typed join ported to T2.
    • @tacit.step.
    • Nullability semantics: filter and join accept Column[bool | None], and assume_not_null() is checked at the output.

      • x: float → Column[float]

  4. Phase 3: tools for teams and agents

    • Agent guide.

Risks and decisions

Risks

  • ibis velocity. The funded team ended in 2024, and the project is maintained part-time. It has been 258 days since the last release. A 13.0 is planned, with breaking changes. Mitigations: pin, test against main, contribute reviews, and keep the exit-plan decision record.
  • Private pandera API in the hybrid. It relies on _check_fn and _check_kwargs, and the switch to the narwhals backend has already moved builtin dispatch once. Mitigations: the parity battery, the narwhals path (already prototyped), and the upstream batching proposal.
  • Generated typing surface. The stubs are about 8.5k lines, but no one edits them by hand. The harnesses fail CI on any lie. Expected human work is 0–2 rule entries per ibis release.
  • Breaking schema syntax. Column[float] and df.c are visible changes. Mitigations: a codemod and a one-release shim.
  • Checker churn. ty is still in beta.

Decisions for the owner

  1. df.c.amount (no collisions, tacit 0.2 spelling) or df.amount (nicer to read, 84 reserved names that grow with ibis). Recommendation: df.c.
  2. Validation option B now plus D upstream (recommended), or C if removing the 2 s pandas import matters more than the pandera ecosystem.
  3. Accept Column[float] instead of float in schemas.
  4. Revisit the "no type checking on examples" rule in CLAUDE.md. With this design the examples are clean on all four checkers, which makes them the regression test for the core promise.
  5. Add pyrefly to the supported checkers. It did as well as mypy in every experiment.
